## 3. The flaky oversized-body test (test-only; included in C11)

**The old test.** `the_indicator_run_route_takes_a_body_between_two_and_four_megabytes_and_refuses_a_larger_one` sent a 3 MB and then a 5 MB request over a real socket to `POST /api/pyind/run`. The route answers 413 and closes the connection **before it has read the body**, so the client's write can meet the connection's reset; `reqwest` then returns a send error (Windows `10053`, connection aborted) and the test's `unwrap()` fails. That is a race in the test, not an answer to the size limit.

## 4. Line endings: an explicit policy, first, limited to named paths

[git-prep/proposed/gitattributes.proposed](git-prep/proposed/gitattributes.proposed) becomes `.gitattributes` in commit **P00**.

- **Source, configuration and documents** (`*.py *.rs *.ts *.mjs *.css *.html *.md *.json *.toml *.lock *.yml *.yaml`, `LICENSE`, `NOTICE`, `.gitignore`, `.gitattributes`): `text eol=lf`.
- **PowerShell** (`*.ps1`): `text eol=crlf` in checkouts (Windows PowerShell 5.1 is the tested interpreter); the repository stores LF.
- **Byte-exact**: `*.patch` and the evidence folders (`baselines`, `agent-probes`, `git-prep/runs`, `maintenance-proposal/runs`) are `-text`: the hashes recorded in the audit records are over those exact bytes. They are also `-whitespace`, so that `git diff --check` does not judge them: trailing whitespace in a patch's context lines or in a recorded log is content (found when the check first ran on the real C14 commit: 142 hits, all in `body-limit-test-hardening.patch`). (Binary files such as images are left to Git's detection; none are tracked today.)
- **Everything else** matches no rule and keeps following each contributor's `core.autocrlf`, as today. Nothing is renormalized everywhere, **no catch-all rule exists** (so no rule can match a protected file by accident), and nothing touches protected files.

**Measured, not assumed** (throwaway clones of the baseline, sparse, no protected file written; runs `…-gitattributes-policy`): every committed text blob at `37f1fc1` has no CR (951 LF, 60 with no line ending, 0 CRLF), so **no existing blob changes**; with the policy added, `git status` shows only the new file and a renormalizing `git add` changes **0 paths**, under both `core.autocrlf=true` (the owner's Windows setting) and `false`; sample files convert as declared (CRLF and mixed endings become LF blobs; `.ps1` blob LF with CRLF checkout; evidence and `*.patch` bytes untouched). The owner's working files are CRLF in 385 tracked files today (autocrlf): the policy changes how future checkouts are written, not what is committed.

Because working copies here are CRLF or mixed in places, **the candidate comparison accounts for the declared policy**: it asks Git for each path's attributes and accepts only the difference that policy produces (section 9), and rejects any other difference, encoding included.

## 6. The inherited protected entry (GP2)

The baseline commit already tracks **one** protected environment-template path. None of the planned commits changes that fact. Therefore:

- The planned check is **not** "zero protected filenames in `git ls-files`" (that cannot pass and is not claimed).
- It is: the candidate's protected entries are **identical to the baseline's** (same path and object id), **no new or changed** protected entry exists, and **none is materialized** in the candidate's working directory.
- **How:** `verify\build_candidate.ps1` clones with `--no-checkout`, writes a non-cone sparse-checkout whose exclusions name each protected tracked path **before the first checkout**, then checks out. The entry stays in the index as skip-worktree metadata. Nothing is opened, read, copied, restored or deleted; only names and object ids are compared; no protected name is printed (output holds counts and booleans).
- **Executed** on the baseline commit (`…-candidate-build-baseline`): 1,011 files on disk (1,012 tracked), **0 protected paths materialized**, 1 skip-worktree entry identical to the baseline, `git status` clean. Use this script for every checkout, clone or worktree of this repository: an ordinary clone or worktree *would* create the file.
- **Alternative (not planned, needs separate authorization):** a metadata-only untracking (`git rm --cached` of that one path in a dedicated commit, leaving the local file untouched, with the ignore rules already covering it). It is not needed to proceed and was not done. The policy is **not** weakened globally.
- CI (proposal) keeps the same rule: `scripts/ci/check_repo_policy.py` accepts only the recorded inherited entry (as a hash of path and object id, no name) and fails on anything else; its tests include a changed inherited entry.

## 7. Which Python code runs: the import-origin proof (GP3)

The owner's `.venv` has an **editable install of the original checkout**, so a bare `python -m athena …` from a candidate would import the original dirty tree: pytest's `pythonpath = ["src"]` only helps in-process, not subprocesses. The gates therefore start every Python process with `PYTHONPATH=<candidate>\src;<verify>\origin_guard`. The guard folder holds `sitecustomize.py`, which at the exit of **every** Python process records where each `athena` module came from; `origin_report.py` fails on any module outside the candidate. Nothing is reinstalled or retargeted in the owner's environment. Limit: an interpreter started with `-I` or `-S`, or a different interpreter, is not observed (the repository has one such use: the user-indicator runner, which does not import `athena`).

**Executed** (`…-origin-probe-sim`): in-process import, a child process started by Python, and `python -m athena.reference` all come from the candidate; the **negative control** (candidate not on `PYTHONPATH`) imports from the owner's original checkout and the recorder flags it. Under the broad suite 17 processes imported `athena` (subprocess-spawning tests included) with 0 from outside; under `cargo test` 39 Python processes were observed with 0 violations (revision 3: those 39 are the Rust tests' own inline Python snippets, none of which imports `athena`, so the Rust gate now proves something different: that the interpreter the tests invoke is the intended one and that the Python-backed tests really started it, section 9).
