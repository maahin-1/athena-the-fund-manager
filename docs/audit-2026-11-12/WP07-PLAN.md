Responses that read the warehouse carry these fields. ### Snapshot and manifest consistency protocol

The data file and its manifest are two files, so two separate replacements can briefly pair the data of one generation with the manifest of another. The protocol removes that possibility instead of hoping the window is short:

1. **Generation-named files.** A snapshot is written as `warehouse.snap.<gen>.duckdb` and an immutable `warehouse.snap.<gen>.json` manifest. Neither is ever overwritten; a new copy is a new `<gen>`.
2. **The manifest pins the data.** It records `generation_id`, the copy's **byte size and content hash** (computed while copying, when every byte is read anyway), `snapshot_created_at` (UTC), `data_as_of` per dataset (read from the copy, not from a file time), the source's size and modification time at copy time, and the job that held the lock.
3. **Validate before publishing.** The supervisor opens the finished copy read-only and runs a trivial query; a copy that fails is deleted and never published.
4. **One atomic pointer.** A single small file `warehouse.snap.current` (naming only the current `<gen>`, size and hash) is replaced atomically. Readers reach a snapshot **only** through the pointer. Because the pointed-to files are immutable and generation-named, a reader that read the pointer sees a consistent pair even if a newer pointer is published a moment later.
5. **Reader checks.** The reader requires pointer generation, manifest generation and file name to agree, the file size to equal the manifest's, and (when the file's size and modification time changed since the last check) the content hash to match. Any disagreement, a truncated or unparseable manifest, or a missing file is `snapshot_inconsistent`: the reader re-reads the pointer once, and if it still disagrees the snapshot is not used and the reason is reported. It never substitutes an invented generation.
6. **Failed replacement.** If a new copy fails, the pointer is left on the previous generation and a status record says `replacement_failed` with the time and reason; the response then says the generation is older than the attempted one.
7. **Cleanup.** The two newest generations are kept; older ones are removed after the pointer moves, and a file a reader still holds (Windows) is retried later, never forced.

**Acceptance:** main readable returns `source=main`; main locked returns the snapshot with `locked_by_writer`, a `generation_id` equal to the manifest's, and `snapshot_created_at` different from `data_as_of` (a copy taken today of data ending last session). Rejection cases, each with a fixture: pointer and manifest name different generations; manifest size differs from the file; the file's content hash differs; the manifest is truncated or invalid JSON; the pointed-to file is missing; the data file replaced after the manifest was written; the pointer moves between a reader's pointer read and its manifest read (the reader still gets a consistent pair); a failed copy leaves the old pointer in place and reports `replacement_failed`. Corrupt main with a consistent snapshot reports the corruption reason; corrupt main and no usable snapshot is an error; two responses from different generations are flagged as mixed.

## T6: bounded queued work

**Implemented (16 November 2026); the review's items T6-R1 to T6-R4 are addressed (stop-first checks and explicit pool shutdown, typed helper results with no duplicate fallback and one deadline and bounded admission on every path, child identity with restart handling and recorded operator and reason, safe operation-kind telemetry) and a second review's five gaps (direct-command cleanup, cancelled waiters, idle-child quarantine, fail-closed recovery, journal transactions) are addressed on 17 November, and a third review's five paths (direct owners in shutdown, reservations after resizing, expired direct requests with one absolute deadline, last-owner drop, a failed journal write that blocks admission, with a retry) on 17 November as well; T6 is CLOSED (17 November 2026, on the reviewer's instruction, with the qualifications in `WP07-T6-CLOSURE-2026-11-17.md` and the T6 record); T8 stays paused:** see [WP07-T6-BOUNDED-WORK.md](WP07-T6-BOUNDED-WORK.md), which maps each acceptance item below to its tests, states the limits and lists the decisions for the reviewer. The plan text follows unchanged.

A bounded queue with a **job ID** and the states `queued`, `running`, `done`, `failed`, `cancelled`, `expired`, `cancel_unconfirmed`. One deadline covers queue wait plus execution; the running time is what remains of it. The existing conservative worker count is kept.

**Acceptance (all with fake children and a controlled clock):**
- **Queue saturation:** a submission past capacity is refused at once with `queue_full` and does not wait; the running job and the queued jobs are unaffected.
- **Expiry before execution:** a job whose deadline passes while queued becomes `expired` (`deadline_before_start`), never starts, and frees its place.
- **Queued cancellation:** cancelling a queued job marks it `cancelled` and removes it, **without touching the running job**, which finishes normally; the order of the others is kept.
- **Running cancellation or timeout:** terminate, wait, kill, wait. When exit is **confirmed**, the worker slot is released.
- **Unconfirmed termination:** when exit cannot be confirmed the state is `cancel_unconfirmed` and the **resource guard (slot, lock, permit) is retained**: no new job takes the worker until the child is confirmed gone or a person resolves it (the same rule T4 now applies to the writer lock).
- One long job plus a queued second job: the second job's advertised timeout includes its wait.
- Per-job queue wait and execution time are recorded (this is the contention measurement that decides the deferred split).

## T8: bounded, redacted diagnostics

One child-process helper for the research jobs. Its stderr handling is a **streaming** one:

- Bytes are read in chunks as they arrive. A hard retention limit applies **during collection**, so an unbounded child cannot grow memory.
- **Redaction is a bounded-memory streaming state machine, not a carry-over tail.** A fixed tail cannot redact a secret-shaped token longer than the tail, so no length-of-pattern guarantee is made. Instead the redactor works on *token runs* (maximal runs of `A-Za-z0-9_-.~+/=` bytes; every other byte, including every non-ASCII byte, is a delimiter) and holds back **at most `M` bytes (default 128) of the current run**, however long the run is:
  - **Decision by shape.** While a run is shorter than `M` the held bytes decide it: a known credential prefix (`sk-`, `sk_`, `pk-`, `rk-`, `nvapi-`, `ghp_`, `gho_`, `ghs_`, `github_pat_`, `xox[baprs]-`, `AIza`) with at least 12 more bytes, or at least 40 bytes mixing letters and digits, makes it secret-shaped. A run that reaches `M` bytes is treated as secret-shaped whatever it contains (**fail closed**).
  - **Decision by context.** A small word-state (no more than the last 24 bytes of word text, lower-cased) recognises introducers (`authorization`, `bearer`, `api_key`, `apikey`, `x-api-key`, `access_token`, `refresh_token`, `client_secret`, `secret`, `password`, `passwd`, `token`) followed only by spaces, `:`, `=` or quotes. The next run after an introducer is redacted whatever its shape and length (`Bearer` after `Authorization:` is itself an introducer and is kept).
  - **Constant memory for any length.** Once a run is decided secret-shaped, `<redacted>` is written once, the held bytes are dropped, and every further byte of the run is **swallowed without being stored**. A token of a gigabyte costs the same `M` bytes and constant time per byte.
  - A run that ends undecided before `M` bytes is released unchanged. At end of stream the current run is decided the same way. Non-ASCII bytes are never held, so a multi-byte character split across chunks is not corrupted.
  - **Output does not depend on how the input was chunked** (tested at every split offset), and the redactor exposes its high-water mark of held bytes so the bound is checkable.
  - **Stated limit:** the design is shape- and context-based. It cannot recognise a secret with no known prefix, no introducer and fewer than 40 mixed bytes (a short free-text password in a sentence), and it redacts ordinary tokens of `M` bytes or more (a very long path or URL) rather than risk a leak. It is defence in depth: the page still shows only short safe messages, and the local log is not an export format.
- **Draining continues after retention fills.** Once the limit is reached the helper keeps reading and **discards** (counting `dropped_bytes`), so the child never blocks on a full pipe and can finish or be cancelled normally. Retained text says it was cut and how much was dropped.
- Each run has an operation ID and timing; the page still gets a short safe message; the local log keeps the bounded, redacted context.

**Acceptance (fake children emitting scripted bytes; no real process needed for the redactor):**
- **Multi-chunk:** every credential shape and every introducer-plus-value form, split at **every** offset into two chunks and (for short inputs) into three, gives output identical to the unsplit input; neither retained text nor the log contains the secret, and the surrounding text survives. An introducer split across chunks (`Authoriz` / `ation: Bearer abc...`), a key, its `=` and its value each in separate chunks, and a prefix split inside itself (`nva` / `pi-...`) are each covered.
- **Long token:** a secret-shaped token of 10 MB delivered one byte at a time, in 7-byte chunks, in 4 KiB chunks and in one chunk yields exactly one `<redacted>` and the same output every time; the redactor's held-byte high-water mark never exceeds `M`; time is linear in the input. The same for a 10 MB value after an introducer, and for tokens of `M-1`, `M` and `M+1` bytes (`M-1` of ordinary letters is released unchanged, `M` is redacted).
- **No over-redaction of ordinary diagnostics:** Python tracebacks, Rust panic text, ordinary words, numbers, and paths and URLs shorter than `M` pass unchanged; multi-byte characters next to a token are intact.
- **Retention boundary:** a secret that straddles the retention limit is never partially retained (an undecided run at the boundary is dropped, not emitted).
- Output far larger than the limit: retained bytes never exceed the limit **at any point during collection** (measured while the child is still writing), and `dropped_bytes` equals the excess.
- **The child keeps running and exits normally after the limit fills** (it is not blocked on a full pipe, and a child that writes more than the OS pipe buffer after the limit completes within its deadline).
- A child that is cancelled or times out after the limit filled still ends through the T6 terminate, wait, kill, wait routine.
- A non-zero exit leaves bounded context locally; the operation ID in the page error matches the local log entry; a multi-byte character split across chunks is not corrupted.

## Verification hygiene for WP07 and later baselines

- **No test writes a runtime file.** `helper.rs` writes `.athena/terminal/helper.log` relative to the working directory. WP07 makes the log location a constructor parameter, so every test passes a temporary directory; until then baselines run from an isolated copy of `terminal/` with its own working directory. An existing runtime file is never "restored" after a run, because a restore can erase entries a running terminal wrote meanwhile; if a run could have touched one, the report says so instead.
- **The web suite is inspected over its full import closure and watched by a tripwire; it is not sandboxed.** Inspection: every test file and every module they import (70 test files, 113 source modules at this baseline) is scanned for network, socket, process, filesystem, storage and URL entry points. Tripwire: a setup file (`guard.setup.v2.mjs`, with a self-test) refuses and records real `fetch`, `WebSocket`, `EventSource`, `XMLHttpRequest`, TCP/TLS/HTTP/DNS/UDP use and child processes, and refuses any filesystem call, including existence and metadata probes, whose path names `.env`, `.env.*`, `*.env`, `.envrc`, a dot-directory (`.athena`, `.venv`, `.git`) or a dot-file. It is a JavaScript guard, not an OS sandbox: it does not cover worker threads started by code, native addons, `process.binding`, descriptors opened before it ran, the vitest/vite main process, or anything started outside `child_process`. Coverage and limits are written out in `GUARD-LIMITS.md` beside the baseline artifacts. Third-party package internals (`fancy-canvas`, `lightweight-charts`, `vitest`, `jsdom`) are not audited line by line.
- **The Rust stage has no run-time guard.** Its isolation rests on inspection of every source file's test code (no test reads a configuration file, an environment file or a runtime store; all stores and logs are temporary directories; sockets are loopback only), an **allowlist-only isolated copy** (`*.rs`, `Cargo.toml`, `Cargo.lock`) used as the working directory, offline locked `cargo`, and a separate short build directory. The test binaries and the project's Python can still read whatever the user can; that is stated, not claimed away.
- **Bypassed tests are reported as bypassed, not as passes.** A Rust test that returns early when its precondition is missing is labelled `ok` by Rust. Every such test is inventoried by name with its precondition (the project Python, or `sh`), the precondition is checked from the isolated working directory, and a test whose precondition was absent is reported as **bypassed**. Where the precondition held, Rust gives no per-test proof that the body ran, so those tests are reported as **precondition met, execution not independently shown**.
- Each broad run saves its collected test IDs, the exact command, the exclusions, toolchain versions and a code-state identification beside the result.

## Revised A6 policy: input freshness for a new verdict

**Today (WP02):** one dataset is gated. A packet whose last price day is more than `price.eod` trading days old (1, counted with the warehouse's recorded no-session days) cannot become a new verdict; `historical=True` is an explicit, recorded exception. Nothing else gates a verdict, although `athena.freshness` declares limits for more datasets.

**Policy, versioned `input_freshness/2` (a proposal for review, not yet implemented):**

1. **Freshness is judged from `data_as_of`, the date inside the data.** Never from a file's modification time, a snapshot's creation time (`snapshot_created_at`), a download time or a database generation. Where only a creation time is known, the input is **`unknown`**, and unknown is treated as not fresh.
2. **Every input has one declared dataset, one limit and one explicit unit** (the unit is part of the declaration and is stored with the result; no limit is a bare number):
   - `price.eod`: **trading sessions**, counted on the exchange session calendar (days recorded as no-session do not count), between the data day and the IST date of the decision.
   - `equity.fundamentals`: **calendar days**, `136`, between the latest statement **period-end date** and the IST date of the decision (one quarter of 91 days plus a 45-day filing allowance, as declared in `athena.freshness`). It is not counted in sessions or weekdays.
   - Boundary rule for every dataset: fresh when `age <= limit`.
   - **Future-dated input is an availability failure, not an age.** Input dated after the decision date (a price day, a period end, a filing or publication date) was not available at the decision. It is **excluded** from the packet where the packet can be built without it (a later statement is dropped and the latest one available at the decision is used; price rows after the decision date are dropped) and **rejected** where it is the whole input (a packet whose latest day is after the decision date is refused with `unavailable_future_dated`). It is never aged, never labelled stale, and never counted as fresh. This uses the same availability rule as `athena.timing.admit` (a publication known only by date counts as available at the end of that date; an unknown publication is not available in a strict case).
   - **`historical=True` waives staleness only.** It lets an old-but-available packet be analysed on purpose, and records that it did. It never waives availability: future-dated or not-yet-published input is excluded or rejected in historical mode exactly as in current mode.
3. **Without an authoritative calendar, blocking inputs stay indeterminate unless freshness is established some other way.** No weekday approximation is used, and no "off by at most one session" assumption is made: a weekday count can be wrong either way (a holiday makes it overstate the age; a special weekend or evening session, such as a Saturday session or Muhurat trading, makes it understate it), so it is not a basis for a blocking decision.
   - **An authoritative calendar** is one with a named source and version whose declared coverage window contains every day from the data day to the decision date, including holidays and special sessions. Days the calendar does not cover are not assumed to be sessions or non-sessions.
   - **Freshness established without a calendar (the calendar-day bound).** Let `d` be the data day and `D` the decision date, both IST dates, with `D >= d` (`D < d` is future-dated and handled above). Let `S(d, D)` be the number of trading sessions on dates `t` with `d < t <= D` (the half-open interval the verdict code already uses for `age_trading_days`). Then

     `S(d, D) <= D - d`   (in days)

     so `D - d <= L` implies `age = S(d, D) <= L` for a limit of `L` sessions, **whatever the calendar says**. That, and nothing weaker, lets a blocking input pass with no calendar, recorded as `basis=calendar_day_bound`.
     **Assumptions the bound rests on:** (1) a calendar date holds **at most one trading day**, so an extra session (Muhurat trading, a special Saturday session) adds a date but never a second count for the same date; (2) age is counted in session *dates*, not in sessions within a date; (3) `d` and `D` are IST dates taken from the data and from the decision clock, not from file or download times; (4) `L` is a whole number of sessions; (5) the limit is `<=`, as declared. If the exchange ever counted two session-days on one calendar date, the bound would be unsound and this policy would have to change before it is used.
     **The converse is not claimed:** `D - d > L` does not mean the input is stale (weekends and holidays make `S` smaller than `D - d`); it means freshness is not established without a calendar, so the result is `indeterminate_calendar` unless an authoritative calendar covers `(d, D]`. Example with `L = 1`: data from today or yesterday passes on the bound; a Monday decision on Friday data (`D - d = 3`) needs the calendar.
   - Otherwise the result is **`indeterminate_calendar`**, and a **blocking** dataset treats it as not fresh (the reason is "no authoritative calendar covers these days"), while a **labelling** dataset labels it `unknown`. It is never `stale` either, because without the calendar staleness is not established.
4. **Statements age from the period end.** When a filing date is known it is shown beside the period end, but the limit is not measured from it. A newer period that has been filed supersedes an older one; "no newer period exists yet" is not staleness before the limit.
5. **Two kinds of consequence, declared per dataset and recorded in the verdict:**
   - `price.eod`: **blocking** (as now): a stale, missing or unknown packet makes no new verdict, asks no model and keeps the last verdict, unless `historical=True`.
   - `equity.fundamentals`: **labelling, not blocking.** A verdict may be made from fresh prices and old statements, but the statement input is marked `stale` (age in days and period end), the fundamental analyst is told so in its packet, and the stored verdict records `stale_labelled` for that dataset. It is never described as current.
6. **Missing and unknown inputs have explicit consequences, never "fresh":**

   | Input state | `price.eod` (blocking) | `equity.fundamentals` (labelling) |
   |---|---|---|
   | fresh | verdict made | verdict made, statement `fresh` |
   | stale | no verdict, no model call, last verdict kept | verdict made, statement `stale_labelled`, analyst told |
   | missing | no verdict, no model call | verdict made **without** a fundamental analyst, `missing` recorded, never an empty packet passed off as data |
   | `data_as_of` / period end unknown or unparseable | treated as not fresh: no verdict | statement `unknown`: verdict made, analyst told the age is unknown |
   | dated after the decision date (future-dated) | rejected `unavailable_future_dated`: no verdict, also in `historical=True` | the future-dated statement is excluded; the latest available one is used, or `missing` if there is none, also in `historical=True` |
   | calendar-day gap above the limit and no authoritative calendar covers the days | `indeterminate_calendar`: no verdict | n/a (calendar days need no session calendar) |

7. **Each stored verdict records, per dataset:** `dataset`, `data_as_of`, `age`, `unit` (`trading_sessions` or `calendar_days`), `limit`, `consequence` (`blocking` or `labelling`), `policy_version`, `calendar` (the source and version used, or `none`), `basis` (`calendar` or `calendar_day_bound`, the latter being the calendar-free proof in item 3), and `status` (`fresh`, `stale_blocked_historical`, `stale_labelled`, `missing`, `unknown`, `indeterminate_calendar`, `unavailable_future_dated`). A verdict stored before this policy stays readable, shown as `freshness: not recorded`, never re-aged or rescored.
8. **Display:** the terminal and dashboard badge each dataset separately (a fresh price beside a stale statement shows both) from the same fields. A panel that mixes generations (T5) says so.
9. **A dataset with no declared consequence is not used by a verdict.** Shareholding, documents, options (`option_chain` 15 minutes is T3's domain) and macro datasets stay out of the verdict's inputs until a consequence is declared; a packet that includes one is a configuration error at policy load, not a silent pass.

**Acceptance, including behavioural tests that make blocking and labelling different in observable ways (fake clock, fake warehouse, fake models, call counters):**
- *Blocking dataset, stale:* the fake model's call count is **zero**, nothing is stored, the last verdict is unchanged, the raised reason names the dataset, age and limit.
- *Labelling dataset, stale:* the fake model **is** called, a verdict **is** stored with `stale_labelled`, and the fundamental analyst's prompt contains the stale statement and its age; the stored rating text never calls the statements current.
- *Consequence is the only difference:* the same stale input run under both declared consequences (the policy object is parametrised in the test) gives opposite results on call count, storage and recorded status. A test fails if a labelling dataset blocks or a blocking dataset only labels.
- Missing and unknown rows of the table above, one test each; a statement period end in the future; the boundary day (`age == limit` is fresh, `limit + 1` is not) in both units.
- Holiday gap with an authoritative calendar (not stale); the **same gap with no calendar** is `indeterminate_calendar` and blocks (it is not passed on a weekday guess and not called stale); a gap within the calendar-day bound passes with `basis=calendar_day_bound` under every calendar, including one with an extra weekend session; a calendar whose coverage window does not contain the days is treated as no calendar; an exceptional weekend session recorded in an authoritative calendar is counted.
- **Future-dated input:** a price packet dated after the decision is rejected `unavailable_future_dated`; a statement with a period end or publication after the decision is excluded and the latest available one is used (or `missing`); a future-dated filing is never aged. Each of these is run with `historical=True` too and gives the **same** result: historical mode waives staleness only, never availability.
- A snapshot with a recent `snapshot_created_at` but old `data_as_of` is stale; an old stored verdict still reads and is shown as not recorded.
- A dataset with no declared consequence supplied to a verdict is rejected at policy load.
