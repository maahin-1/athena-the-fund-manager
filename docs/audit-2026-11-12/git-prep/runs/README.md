**Harness defects found while writing the review-3 regressions (kept, fixed, never silently):**

* The first run of the checkout-script tests used Git Bash's own `git` instead of the recording stand-in (Git Bash puts its git first on PATH). A hostile `REMOTE_URL` was then really attempted (a DNS failure for the override host; no credential was involved) and an inherited `GIT_CONFIG_COUNT` really redirected the fetch to another host. **That was attempted network access.** The lack of a real credential does not make it an offline fake run, and that first run is excluded from every offline-isolation claim in these documents (the corrected runs, with the recording stand-in in front, are the ones that stand). It showed R1 for real, but the harness was wrong: the stand-in is now put in front through `BASH_ENV`, and a guard test fails if the stand-in is not the git that runs.
* `bash -c` fed through Python's argument list on Windows halves doubled backslashes, so a probe of the escape line through that route could not see the doubled backslash the line contained. The line now uses `\x5c` and means the same whether bash reads it from a file or from an argument.
* **A real defect in my first version of the new script, caught by its own test:** the case-insensitive match of protected names was enabled for the whole script, and it also made the SHA check accept upper-case hex (`=~` obeys it). It is now confined to the name predicate.
* **A wrong conclusion of mine, corrected:** my first probe passed the escape line to bash as an argument, and the output showed every pattern character replaced by a literal `&`. I took that for a defect of the script. It was the argument route (Windows halves doubled backslashes there); read from a file, the old line escaped brackets, stars, question marks and backslashes correctly. The one real defect in that line was a trailing space, which it did not protect. The documents say so; the line now spells its backslash as `\x5c` so that it means the same on both routes.
* The first listing file was written inside `.git`, which the recording stand-in never creates; it is now a temporary file.
* Git for Windows refuses `*` and `?` in any path (and `\` is rewritten to `/` in a path argument), so those characters are covered by the escape probe, not by a real checkout, on this machine.
