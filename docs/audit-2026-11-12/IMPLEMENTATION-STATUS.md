## Q6 — tied votes divide by zero

**Current mechanism (confirmed in source):** `src/athena/evaluation/pit_score.py`, `score()`: `modal()` returns `neutral` for a bullish/bearish tie, then the confidence was averaged over the runs whose signal equals that chosen `neutral`. With no observed neutral run the denominator was zero. `src/athena/evaluation/scorecard.py::cases` already handled the same situation (confidence 0.0).

**Reproduced:** `test_opposing_votes_with_no_neutral_run_do_not_crash_and_the_synthetic_neutral_has_zero_confidence` failed on the unmodified code with `ZeroDivisionError: division by zero` at `pit_score.py:82` (1 failed, 11 passed before the fix).

**Change:** `src/athena/evaluation/pit_score.py` only. The confidence of the chosen signal is averaged over the runs that actually gave it; when none did (a synthetic tie-to-neutral) it is `0`, the same as `scorecard.cases`. `modal()` is untouched, so ties still resolve to neutral. No shared helper was introduced: the two consumers already keep their own semantics and agree.

**Semantics now explicit (tests):** two opposing votes and four evenly opposing votes: one case, mix 100% neutral, confidence 0, so not counted as a high-confidence call, agreement = 0 (the runs disagreed). Observed-neutral majority: its own average confidence (80/60 -> 70, a high-confidence call). Tie including an observed neutral: that neutral's confidence, not 0. Three-way tie with an observed neutral: that neutral's confidence. All abstained: 0 cases, 1 abstained, agreement `None`. Single run: 1 case, agreement `None`.

**Compatibility / data impact:** valid cases score exactly as before (the whole existing module and scorecard suite pass). Only the previously-crashing case changes (now a result). No stored results were rescored or rewritten.

**Limit:** a synthetic neutral is still scored as a neutral call for accuracy. That is the stated existing policy ("the call that commits to least"), not changed here.

## T4 — terminate, reap, then release the lock

**Current mechanism (confirmed in source):** `src/athena/ops/supervisor.py::Supervisor._run`. Timeout branch: `proc.terminate(); code = 124; return`: no wait at all, then the `finally` released the writer lock. Parent-gone branch: `terminate()`, `wait(20)`, `kill()` on timeout and then returned with no confirmation. Locks are pid files holding the **supervisor's** pid, so releasing them advertised the writer free while a live child could still be writing. A `terminate()` that raised (`ProcessLookupError`) escaped entirely.

**Reproduced:** with the two new constants injected the unmodified code produced the call lists `['terminate']` (timeout) and `['terminate', 'wait(20)', 'kill']` (shutdown): no bounded wait, no confirmation after kill, lock released straight after. 5 of 17 supervisor tests failed before; the four behavioural ones were confirmed with `scratchpad/t4_probe.py`.

**Change:**
- `supervisor.py`: `end_child()` is the single shared path for timeout and parent shutdown: terminate -> bounded wait (`TERMINATE_WAIT` 20 s) -> kill if still alive -> bounded wait (`KILL_WAIT` 10 s). It returns True only when exit is confirmed by a returned `wait`/`poll`; an OSError from a signal is not treated as confirmation. The lock is released by the existing `finally` only after this returns. Exit codes stay `124` (ran past `max_hours`, a job failure that backs off like any failure, distinct from the exchange/model/store/lock codes 3-6) and `130` (software closed, health not judged). A timeout row also records `last_reason: "timeout"`.
- If the child still cannot be confirmed: `Job.hand_over(pid)` (new, `jobs.py`) rewrites each held lock in the **child's** pid with an "exit unconfirmed" note, so it keeps refusing other writers while that process lives and is taken over normally once it is gone. The supervisor records `unconfirmed_child {pid, since, ended_because}` on the task row and sets the job status `failed` with a message. A second job needing that writer receives code 6 (lock held, retry soon). (The first version of this handover left the lock in the supervisor's name when the rewrite failed or no pid existed, which the next job in that supervisor could reclaim; superseded by the follow-up below.)
- `Supervisor.__init__` gained `status_dir` / `lock_dir` (defaults unchanged) so tests use temporary directories.

**Regression:** `tests/test_supervisor.py`: timeout with exit on terminate; child that ignores terminate (kill, confirmed); child never confirmed (lock handed to the child pid, row and status record it, second job refused with 6, lock taken over once the child has gone); software-closed path with the same sequence; `terminate()` raising; natural exit with no signal; no stale `unconfirmed` carried into the next job. Each asserts the lock file still exists at every `terminate`/`wait`/`kill` call. `tests/test_ops.py::test_handed_over_locks_stay_in_the_childs_name_and_free_up_only_when_it_is_gone`. Fake processes only; no real sleeps or children.

**Compatibility / data impact:** exit codes, state-file keys and defaults are unchanged apart from additive `last_reason` / `unconfirmed_child`. A run that previously "timed out" instantly now takes up to 30 s longer in the worst case (20 + 10 s bounded waits) before the lock is released.

**Remaining limits:** only the **direct child** is ended and reaped. Grandchildren are not tracked (no process group / Windows job object); the jobs run in one process, and this is documented in `end_child`. A hung kill leaves the lock held in the child's name until the process disappears; there is no further automatic escalation. Real `Popen` behaviour on Windows was not exercised (fakes model `wait(timeout)` raising `TimeoutExpired`).

### T4 follow-up — an unresolved handover must keep blocking writers

Source: [BATCH-1-REVIEW.md](BATCH-1-REVIEW.md), P2. The first T4 fix made `Job.hand_over()` swallow a failed lock rewrite and clear its held list unconditionally, and with no usable pid it rewrote nothing. In both cases the lock file still named the supervisor. `_take()` treats a lock naming the current pid as reclaimable, so the next job in the same supervisor deleted it and started a second writer beside a possibly-live child; and a supervisor that ended later made the same file look stale.

**Reproduced (before the follow-up change):** a standalone probe (`scratchpad/t4_handover_probe.py`: temporary directory, injected `OSError` from `athena.ops.jobs._write` on lock files only, fake pid 424242, no child process, no database) printed `rewrite fails: hand_over returned None; second writer admitted: True` and `no usable pid: hand_over returned None; second writer admitted: True`. This matches the reviewer's reproduction. After the change the probe prints `HandOver(... failed=(('writer:sample.duckdb', 'OSError: ... No space left on device'),))` / `quarantined=('writer:sample.duckdb',)` and `second writer admitted: False` for both.

**Design (src/athena/ops/jobs.py, supervisor.py):**
- `Job.hand_over(pid)` now returns a `HandOver` outcome per lock: `transferred` (lock file rewritten in the child's pid), `quarantined` (no child pid: record written with `child_pid` 0), `failed` (file could not be written, with the error text). `ok` is true only when every lock was transferred. The outcome is stored on the job's status file (`handover`).
- Every handed-over lock is an explicit `state: "unresolved"` record carrying `child_pid`, `supervisor_pid`, `since` and a note. `Job._take` **never** reclaims one because its supervisor is this process or has ended. It is freed only when `child_pid` is known and that process is confirmed gone (`pid_alive` false), or by `jobs.clear_unresolved(lock)`, the operator's explicit decision (nothing calls it automatically). An unknown child pid is never assumed dead.
- If the lock file cannot be written, the lock is remembered in this process (`jobs._QUARANTINE`, keyed by lock path) and `_take` refuses it from there, whether or not a file exists. It is reported in `failed`, not dropped. A lock whose file is no longer held by this process is also reported failed.
- The supervisor records the outcome in `self.unconfirmed`, in the task's `unconfirmed_child` state row (now with the child pid and the full list of lock names), and in the job status `last_error`: "... lock handover incomplete: lock file not written for <lock> (OSError: ...) (blocked in memory only)", so a lock-storage failure is visible in status and diagnostics. The status state stays `failed`; the exit code stays 124/130.
- Restart: `Supervisor.recover()` runs at the start of `run()`, before anything is scheduled. For every task row with `unconfirmed_child`, if the child pid is alive or unknown it re-installs the unresolved lock records (`jobs.reinstate`, which never overwrites a lock a different running job holds; such a lock is reported failed); if the pid is known and gone it clears the row. Locks it cannot write are listed in `recovery_errors` and `supervisor.json["recovery_warnings"]`, and are still refused in memory. So an old supervisor that ended while its child was unresolved does not make the writer look free.
- Bounded shutdown and the successful-transfer behaviour are unchanged (same terminate/wait/kill/wait; transferred locks still carry the child's pid and an "unconfirmed" job note).

**Regressions** (fakes and temporary paths only; each asserts the next writer was **not launched**, by counting spawn calls): `tests/test_supervisor.py`
- failed rewrite: the file still names the supervisor, the failure and error text reach the status `last_error` and the state row, the next job in the same supervisor gets code 6 with zero launches;
- missing/unusable pid: lock marked unresolved with `child_pid` 0, refused in the same supervisor and after the file is rewritten to name an ended supervisor, and freed only by `clear_unresolved`;
- partial success across two locks: one transferred, one failed; outcome and status report each; jobs wanting either lock or both are refused;
- restart while the child is unresolved: the lock file now names a dead supervisor and the in-memory block is gone; `recover()` reinstates it from `supervisor.json`, the writer is refused, and when the child is finally gone recovery clears the row and the writer runs;
- recovery with an unknown pid keeps blocking; a reinstatement that cannot be written is reported in `recovery_errors` and still refused in memory.
`tests/test_ops.py`: `hand_over` outcomes, the unresolved-lock rules (supervisor ended with the child alive, child pid unknown, child pid gone, `clear_unresolved` once), failed rewrite on two locks, and `reinstate` not overwriting a running job's lock. **Mutation check** (`scratchpad/t4_mutation.py`): with the unresolved guard and the in-memory block neutralised, 8 of these 9 tests fail (the ninth, `reinstate` never overwriting a running holder, does not depend on them).

**Compatibility:** successful handover keeps its lock-file keys (`pid` = child, `job` note containing "unconfirmed", `since`) and adds `state`, `child_pid`, `supervisor_pid`, `note`; `handed_over_by` was renamed `supervisor_pid` (internal to one unmerged batch). Normal locks and normal job runs are untouched. New additive state keys: `unconfirmed_child.locks`, `unconfirmed_child.handover`, `recovery_warnings`. No production `.athena` lock, state or status file was opened.

**Remaining limits:** an unresolved lock with an unknown pid blocks until the operator resolves it (there is deliberately no timer; the durable operator command was added in follow-up 2 below. `jobs.clear_unresolved` alone clears only the lock and is not the operator path). If the lock file, the in-process memory **and** the supervisor state file all fail, nothing durable remains across a restart; the failure is still reported in status. `pid_alive` is pid-based, so pid reuse could keep a lock blocked longer than needed (safe direction) and cannot free one early. Direct child only, as before; fakes model `Popen`, not a real hung job.

### T4 follow-up 2 — unresolved-child records survive blocked retries and are cleared only durably

Source: [BATCH-1-REVIEW.md](BATCH-1-REVIEW.md), second P2. `Supervisor.step()` removed a task's `unconfirmed_child` whenever the current `_run` set no new one. A scheduled retry refused by the quarantined lock (code 6) launches no child, so it says nothing about the earlier one, yet it deleted the only durable record. After a restart `recover()` had nothing to reinstate and a writer launched beside the still-live child. It needed only the lock rewrite to have failed, not all storage.

**Reproduced:** the new sequence test (`test_failed_handover_then_a_blocked_retry_then_a_restart_still_refuses_the_writer`) failed on the follow-up-1 code at the first assertion after the refused retry: `KeyError: 'unconfirmed_child'` (`last_exit` was 6 and the record was gone).

**Change (src/athena/ops/supervisor.py, jobs.py):**
- Per-attempt result and outstanding child lifecycle are separate. `unconfirmed_child` on a task row is lifecycle state: the newest unresolved child, with `previous` holding older ones (`unpack`/`pack`). No run (refused, failed, succeeded, stopped) removes it. `step()` keeps every record that is still open and puts a new one in front, so a second unresolved child does not overwrite the first.
- A record leaves only by (a) a **confirmed exit**: a known pid that is no longer running, checked in `step()` and `recover()`; an unknown pid is never confirmed; or (b) **durable operator resolution**: `resolve_unresolved(lock)`, also `python -m athena.ops.supervisor --clear-unresolved LOCK`. It first removes the lock from every unresolved-child record in `supervisor.json` (a record left with no lock to guard is removed; `operator_cleared` and an `operator_resolutions` audit entry with the time are written), saves, and only then removes the lock file and the in-memory block. Saving failure raises and leaves the lock blocked. So startup recovery cannot reinstate what was cleared, while clearing one of a child's locks leaves its other locks guarded.
- `recover()` now reads every record in the chain, drops only the confirmed-gone ones, and reinstates from the durable list of locks (an emptied list reinstates nothing; only a legacy record with no list falls back to the task's locks).
- `step()` first calls `jobs.sync_quarantine`, so a block that exists only in a running supervisor's memory follows an operator's durable clear made by another process.

**Regressions** (`tests/test_supervisor.py`, fakes and temporary paths; each asserts no writer was launched by counting spawn calls): the review's sequence (failed handover -> ordinary `step()` returns 6 and the record is still there -> restart with memory gone and the lock file naming an ended supervisor -> writer still refused -> child confirmed gone -> record cleared and the writer runs once); an unknown-pid record surviving three refused retries each followed by a restart, then `resolve_unresolved`: the recovery record is gone, the audit entry is written, the lock file is gone, and a further restart does not reinstate it and the writer runs; clearing one of two locks leaves the other guarded after a restart (even with its lock file deleted); a running supervisor drops a memory-only block after another process clears it durably; two unresolved children of a lock-less task are both kept and dropped only as each is confirmed gone; the `--clear-unresolved` command updates the saved state. **Mutation checks** (`scratchpad/t4_mutation2.py`): with `step` dropping records (the reviewed behaviour) 7 tests fail; with an operator clear that touches only the lock file 3 tests fail.

**Compatibility / data impact:** `unconfirmed_child` keeps its place and meaning; it may now also carry `previous` and `operator_cleared`, and `supervisor.json` may carry `operator_resolutions`. These keys come from this unmerged batch; no production state file was read or written. The command and function are new surface.

**Remaining limits:** `resolve_unresolved` loads and saves the whole state file, so running it while a supervisor is mid-step has the same last-writer-wins window as the supervisor's own saves; a running supervisor picks the clear up at its next step. A record with no locks and an unknown pid guards nothing but never auto-resolves (a real `Popen` always has a pid; fakes can omit it). Pid-based confirmation: a reused pid can only keep a lock blocked longer (safe direction). Direct child only, fakes only, as before.

## T7 — startup stops on a failed native command

**Current mechanism (confirmed by running a copy):** `scripts/terminal.ps1` sets `$ErrorActionPreference = 'Stop'`, which in Windows PowerShell does not turn a native command's nonzero exit code into an error. A failing `npm install`, `npm run build` or `cargo build` fell through to `Start-Process` and launched whatever `athena-terminal.exe` was already on disk. ### B2-1 (P1) — an unknown send outcome is kept on record

**Confirmed mechanism:** `_confirm` removed the SENDING marker in an unconditional `finally`, including when `broker.place` raised after the order may have reached the broker; `resume()` read only that marker and ignored
the adapter's own `unresolved()` ledger, and nothing stopped a *different* order while that ledger was non-empty.

**Change (`src/athena/brokers/desk.py`):**
- The marker now has a `state`: `sending` (in flight), `outcome_unknown` (the send failed after it may have been accepted: timeout, lost answer, an answer with no order id, any error that is not a refusal) and
  `placed_unlogged` (the order exists, its audit line could not be written; the error to the caller names the order id). It is rewritten in one step, never removed while the outcome is unknown, and **kept on a
  `KeyboardInterrupt`/`SystemExit` during the send**.
- Only a *known* outcome releases it: a normal completed send, a refusal before `place` was called, and a broker refusal that carries an HTTP 4xx status (`_is_definite_refusal`; this matches the adapter's own rule
  for marking an entry `refused`).
- The adapter's unresolved ledger is consulted everywhere the marker is: a new send (`_claim_send`), the preview (a blocking `no unresolved send` finding, for any broker that keeps such a ledger), `kill()` and `resume()`.
  A ledger that cannot be read is reported as unresolved ("could not be read"): it cannot show that nothing is unknown.
- `resolve_send(note)` clears both together and writes one `send_resolved` audit line carrying the earlier marker and the resolved ledger keys. It refuses, changing nothing, when the ledger cannot be read; the marker is

## Batch 3 — WP04 steps 1-3: immutable statement versions (Q3)

Authorised scope: migration tooling and copied-store dry runs only; the real `.athena` store was not opened, copied or migrated. Steps 4 (dated shares/rates/industry/membership) and 5 (frozen cohorts, suspended
terminal cases) are **not done** and stay `open` (see "Not claimed").

**Confirmed mechanism (Q3):** `FundamentalsStore.save_statements` deleted an older filing's row when a newer filing arrived for the same key, and kept the newer row when an older filing arrived second; the ingest's `wanted()` also
fetched only the latest filing of a period. The original value was therefore not stored, and `AsOfFundamentals.lines` filtering that table by `filed <= cutoff` made a revised period drop out.

**Model (`src/athena/fundamentals/store.py`):**
- `statement_lines` is unchanged and remains the **latest-value table** the current pages read (same writes, same replacement rule). Nothing that reads it changed.
- `statement_versions` (new, append-only): one row per company, basis, statement, period, line and **filing**, with `filed` (when public), `ingested` (when this system stored it, NULL if unknown), `source_hash` (sha256 of
  the raw filing), `parser_version` (a hash of the parser and the line mapping, so it changes by itself), `layout`, `provenance` (`ingest`, `rebuilt_from_raw`, `seeded_from_latest`) and `migration_id`. `save_statements`
  writes every offered row to it in the same transaction, including a filing that arrives after a newer one (its original is no longer lost). Re-reading a filing (`forget_filing`) replaces that filing's versions with the new reading.
- `lines_as_of(symbol, basis, statement, cutoff, fieldwise=False)`: for each period the latest eligible filing (filed by the cutoff, not withdrawn by it); **whole-filing** by default so a partial amendment is exactly what it
  reported and inherits no contradictory lines; `fieldwise=True` takes the newest eligible value of each line. Ties go to the greater filing identity, so insertion order never decides. `gaps_as_of` lists periods the store holds a
  version of but none public at the cutoff, with the reason (a missing original shows here). `withdraw_filing` records a withdrawal (visible to cutoffs before it, not after) and rebuilds the latest table from the remaining versions;
  `rebuild_latest` refuses unless every latest row is also a version. Basis is part of the key and the layout is stored per version, so basis and layout changes stay distinguishable.
- Schema versioning: `schema_meta('statement_versions', 1)`; opening a store with a newer value for writing is refused.
- Ingest: `wanted(..., all_versions=True)` / `ingest --all-versions` also fetch the original of a revised period (one extra request per revision; **off by default**, so network behaviour is unchanged). Every ingest now records the raw filing's hash.

**Migration tool (`python -m athena.fundamentals.vintages`):** dry run by default (read-only open, counts, nothing created). `--copy-to` makes a byte copy (never over an existing file) and works on it; `--apply` needs `--copy-to` or
`--in-place`; `--rollback ID --in-place` removes exactly one migration's rows. It writes only `statement_versions`/`migrations`, never `statement_lines`. Sources, and nothing else: rows now in the latest table, copied as
`seeded_from_latest` (not known to be the original, no ingest time or hash); filings recorded `ok` that have **no version yet** and whose raw copy is still kept in the ingest cache, re-read as `rebuilt_from_raw` with the raw hash.
A filing with neither a raw copy nor a surviving row is listed under **originals unavailable** and stays missing: today's restatement is never relabelled as the original. One transaction (a failure writes nothing), recorded in
`migrations`, idempotent (a second run adds zero). **It refuses the default store `.athena/fundamentals.duckdb` in every form, a dry run included.**

**Research reader (`valuation/calibrate.py`):** `AsOfFundamentals(..., policy=)`: `vintage` (strict, from the versions; raises if the store has none, since an empty answer would read as "no statements"), `latest_filtered` (the old
approximation, kept and labelled), or `auto` (vintage when the store has versions, else the labelled approximation). `build_snapshot(statement_policy=)` records the policy used in `Snapshot.statement_policy`.

**Regression:** `tests/test_fund_vintages.py` (25): the acceptance case (100 filed 2024 and 120 filed 2025 read 100 at a 2024 cutoff, 100 before the revision, 120 after, and the current page still 120); an older filing arriving second;
duplicate saves; provenance fields; partial amendment whole-filing versus fieldwise versus current page; deterministic ties; withdrawal; basis and layout; a missing original reported unavailable; dry run changes nothing (file
hash); seeding with honest provenance and an unchanged current page; idempotent re-apply; rebuild only from a kept raw filing; a missing original stays missing; rollback removes only the migration's rows and the current page is
the same before and after; unknown migration refused; failure part-way leaves nothing; newer schema refused; copy leaves the source byte-identical and never overwrites; in-place and default-store refusals; the command's output;
both research readers; `wanted(all_versions)`; ingest writing the hash. One existing test (`test_val_calibrate.py`, a fake with only the latest table) now names `policy="latest_filtered"`. Mutations: as-of reader back to the
latest table 7 fail; ingest writes no versions 12 fail; missing originals not reported 2 fail; migration rewriting the latest table 3 fail.

**Compatibility impact:** the first time a writer opens a store with this code (an ordinary ingest), three additive tables are created and new filings start writing versions; `statement_lines` and every reader of it are untouched.
The versions of that store are empty (strict as-of reads raise, `auto` falls back to the labelled approximation) until the owner runs the migration, which needs separate authorisation. Backup first (`ops/backup.py` conventions) and

### A1 — a figure is bound to a fact, or the output says it is not

**Current mechanism (confirmed in source, and in the audit's probe):** `evaluation/grounding.py::check_grounded` asks whether a number written in the prose appears *anywhere* in the packet. It strips the sign, scales by 100

**Change:**

- Council (`council/evidence.py`, `debate.py`, `judge.py`): a figure written in a case or judge reply that is the value of a fact on the sheet must belong to a fact the reply cites (a fraction may be read as a percent;

  sheet shows each analyst's typed claims (`fact (written by code): ...`) and the scheme that checked it.

**Decision recorded:** the typed contract is opt-in, not the default. A default change alters every analyst's prompt and cannot be validated without model calls, which are out of scope; flipping it is a decision to make with

## Batch 4 — WP06: durable budget reservations and reproducible run envelopes (A5)

**Current mechanism (confirmed):** `Meter.rows()` returned `[]` for the whole file on any bad line (the audit's reproduction: one valid call, ceiling 1, append `{partial`, the count becomes 0 and the next call is allowed);

**Change:**
- `llm/ledger.py` (new): SQLite reservations taken inside `BEGIN IMMEDIATE`, so two processes cannot both take the last slot. Units are separate: a **logical request** (one reservation; what `calls_per_month` counts, not provider
  attempts, tokens or money), a **provider attempt** and a **retry** (rows under the reservation), and **token usage** (NULL when the provider reported none, never zero). States: `reserved` (counts, and keeps counting if the

  usage, unresolved reservations, and `--release ID --by NAME --why TEXT` closes one. `MeteredLLM` reserves before it asks.

- `llm/envelope.py` (new) and `llm/cache.py`: a `RunRecorder` (context variable) collects each logical request without changing callers: exact responding model (`unknown` when not reported), attempts, usage (`unknown`, never an

## Batch 4 review corrections ([BATCH-4-REVIEW.md](BATCH-4-REVIEW.md))

An independent review ran 233 focused tests (all passed) and reproduced four gaps that those tests did not cover. All four are reproduced here as failing synthetic tests, fixed, and mutation-checked. Nothing live was run.

### B4-1 (P1) — a reply that was not what was expected is not a refusal

**Reproduced:** `{"choices": [{}]}` as an HTTP 200 raised `KeyError` before an attempt was recorded; the chain reported no attempts, the ledger read an empty history as "every attempt was declined" and refunded the unit. With
a ceiling of one, two requests both reached the transport.

**Change:** `llm/client.py` records each request as `sent` *before* it goes out and settles it afterwards, so the history is never empty once a request may have left, and an interruption or surprise in between leaves it
`sent` (counted). `_read` validates every shape (choices, first choice, message, content, usage) and raises a retryable `ProviderError` (`bad_reply`, status 200) for any that is not usable; token usage is kept only when each
figure is a finite non-negative number, otherwise it stays unreported (never `int()` of NaN). `llm/router.py`: a client that was called and reports no request is recorded as `unreported`, so only a model that was skipped without
being called contributes an empty history (still free). `classify_failure` is unchanged: `sent`, `bad_reply` and `unreported` are not declined answers.

**Tests:** `test_llm_replies_unexpected.py` (35): ten malformed 200 bodies each count and block the second request before any transport call; each is a recorded `ProviderError`; retry of a malformed reply; `KeyboardInterrupt`,

### B4-2 (P2) — an unrelated known row cannot lend its source to a relevant unknown one

**Reproduced:** support citing a known-source row with an unrelated value (55) and an unknown-source row holding the relevant value (1000) was assessed `independent, statements:TARGET`, because sources were unioned over all

## Batch 5 — WP07 T5: snapshot generations and provenance

Scope: T5 only. Synthetic stores and temporary paths only; no production `.athena` data, environment file, live call, commit or push. Plan and the reasoning behind each choice: [WP07-PLAN.md](WP07-PLAN.md).

**Current mechanism (confirmed):** `refresh` copied the warehouse to one file `warehouse.snap.duckdb`, replacing it in place; a reader opened it whenever the real file failed to open, for any reason, and reported nothing about it. A failed replacement kept the older copy silently. No reader could say which data it had, when the copy was taken, or what date its data stopped at.

**Change:**
- `src/athena/warehouse/generations.py` (new; the specification of the protocol): files `X.snap.<gen>.duckdb` (immutable copy), `X.snap.<gen>.json` (immutable manifest: generation id, file name, byte size, SHA-1 and SHA-256 computed while copying, creation time, the source's size and modification time, the job that held the lock, and `data_as_of` read **from the copy**), `X.snap.current` (the pointer, the only file replaced, atomically), and `X.snap.status.json` (**the last publication attempt, separate from every manifest**). Writer stages: copy while hashing, validate by opening the copy, manifest, pointer, cleanup. A failure before the pointer moves leaves the previous pointer, manifest and copy byte for byte as they were and removes that attempt's files; cleanup runs after the pointer moves and aims to keep the two newest generations (a **nominal retention target, not a disk-space ceiling**: a file a reader or scanner holds on Windows is deferred and reported, never an error, and a crash can leave orphans, so more files can remain until a later publication removes them). Reader (`resolve`): the pointer is read once, then only the immutable files it names are used, and pointer, manifest, file name, size and content hash must agree, or the result is an explicit `SnapshotUnavailable` (`absent`, `pointer_invalid`, `manifest_invalid`, `mismatch`, `size_mismatch`, `hash_mismatch`, `vanished`, `unreadable`). A generation removed between the pointer read and its use is retried once through a fresh pointer read; a briefly locked small file (Windows, during an atomic replace) is retried a few times before it is `unreadable`.
- `src/athena/ops/snapshot.py`, `ops/supervisor.py`: `refresh` publishes a generation (same return meaning: True only when a new one is in place) and names the job about to hold the file in the manifest.
- `src/athena/warehouse/warehouse.py`, `chart_bars.py`: `Warehouse` reads only a validated generation when the file is locked, and exposes `provenance` (which source answered, and why); the chart helper reports it.
- `terminal/src/snapshot.rs` (rewritten): the same checks in Rust (SHA-1 from the crate already in `Cargo.lock`; no dependency changed), `open()` returning the connection **and** provenance, `open_read_only()` keeping its old contract (a connection, or the real file's own error), a classifier of why the real file failed (`main_missing`, `locked_by_writer`, `main_unreadable`), and a registry of what each reader last got. `bars.rs` opens the warehouse **once per response** (it used to open it up to several times, which could mix generations within one answer) and returns the provenance; `analysis.rs`, `fundamentals.rs`, `search.rs`, `calendar.rs` name themselves as readers. `server.rs`: daily bars carry `provenance` (existing `source` and `note` wording unchanged), a new `GET /api/data-source` reports each reader's last answer and whether recent answers came from different generations (same origin rules as every API route).
- `terminal/web/src/provenance.ts` (new), `panels/chart.ts`, `main.ts`, `style.css`: the chart note says "Snapshot, because …: copy taken <time>, data to <date>" (creation time and data date are two facts), failures say why no data is shown, and the shell shows a badge: empty while every reader has the real file, "snapshot while updating", "mixed data generations", or "warehouse unavailable". A server that says nothing leaves the badge empty; nothing is claimed.

**Provenance fields:** `source` (`main`/`snapshot`), `source_path`, `generation_id` (a snapshot's comes from its manifest; a main file's is `main:<size>:<modified ns>`, labelled `generation_basis: observed`), `snapshot_created_at`, `data_as_of` (for a daily answer, the date of the last bar it returned; the manifest's per-dataset dates are kept as `snapshot_data_as_of`), `fallback_reason`, `validated`, `snapshot_status`, and for a failure `failure.{main_reason, snapshot_reason}`.

Evidence, one directory per run and nothing overwritten: [baselines/wp07-t3-2026-11-16/](baselines/wp07-t3-2026-11-16/README.md). No production data, environment file, live call, commit or push.

**What the audit found (T3):** one fresh option could label a chain live while stale contracts still produced a volatility and Greeks from economically inconsistent inputs; the badge followed the newest quote; a last-trade time was the only time kept.

**Times, kept apart per contract** (Rust `deriv_quotes.rs`, the `/api/derivs/quotes` rows and socket frames):

| Field (page name) | Meaning | Moves when |
|---|---|---|
| `t` (`time`) | the exchange's time of the last **trade** | a packet carries a newer trade |
| `r` (`receivedAt`) | the server's receipt of the packet that gave the quote its present content | the content changes; a **repeat of the held quote changes nothing and does not make it newer** |
| `bs` (`bookSeenAt`) | the server's receipt of the last change of the best bid or ask. **The broker stream carries no exchange time for the book**, so this is a receipt time and every decision says so (`bookTimeBasis: book_seen`); a source that gives an exchange book time (`bookTime`) is preferred | the best bid or ask changes. A trade at an unchanged book does **not** refresh it, and a new bid with no new trade does not move the trade time |
| `dly` (`deliveryDelayMs`) | receipt less exchange time of a packet that carried a **newer** trade; null on first sight (it may be an old trade) | a newer trade arrives |
| `ooo` (`outOfOrder`) | packets discarded because their exchange time was older than the held quote's | an older packet arrives: it is **discarded and counted, never applied**, and moves no time |

Every contract has its own record: a packet for one contract touches no other's. The quotes route also returns `now` (the server's clock) and the page measures ages in it (`serverNow`, from the answer or from the socket frame's `sm`), not in a clock that may disagree.

**The policy** (`terminal/web/src/options/quality.ts`; `POLICY_V1`, version 1; each decision records `{id, version}`):

| Rule | Limit (v1) | Consequence |
|---|---|---|
| Book age (`age <= limit` fresh) | 15 minutes (the `option_chain` limit of `athena.freshness`) | `stale_book`: **withhold** |
| Two-sided book required (bid and ask above zero) | required | `no_two_sided_book`: **withhold**; a last trade is **not** used in its place |
| Crossed book (bid above ask) | | `crossed_book`: **withhold** |
| Wide book ((ask - bid) / mid) | 25% | `wide_book`: **label** |
| Book time unknown (a source or older server with no book time) | | `book_time_unknown`: **label**; never called fresh, and the trade time is never used for the book |
| Old trade as the price (only where the policy does not require a book) | 15 minutes | `old_trade_price`: **withhold** |
| Delayed trade (`dly`, at the limit is fine) | 5 seconds | `delayed_feed`: **label** |
| Out-of-order packet discarded | any | `out_of_order_discarded`: **label** |
| Last session (no contract's exchange time has advanced lately) | | `session_observation`: **label** ("an observation, not a tradable price"); ages are measured from the newest receipt seen, so a quote older than that is still stale |
| Forward: no source, stale input, or time unknown | no forward / 15 minutes | `no_forward`, `forward_stale`: **withhold**; `forward_age_unknown` (from spot, which carries no time): **label** |
| Forward and option out of step (`gap <= limit` is in step; compared only for a book that is itself fresh) | 5 minutes | `forward_unsynced`: **withhold** |

**The distinction the audit asked for:** an old **trade** beside a fresh book is not stale (the volatility is read from the book and the decision records `trade: old`); a recent trade beside a stale book is stale. Receipt of a packet is recorded but is never used as the book's age, because a trade alone moves it.

**The forward** is the future when the future's own quote passes the rules; otherwise the one implied by the options that pass (a stale or one-sided pair is never an input); otherwise spot grown at the rate (labelled: it has no time). A source that was passed over is recorded with the flags that failed it (`quality.forward.rejected`). The forward's time is the **oldest** of its inputs. **The chain's badge is its worst required input** (the forward and the at-the-money call and put), never its newest quote: `quality.status` is `ok`, `labelled` or `withheld`, with `worst`, the per-input list, the count of contract sides in each state, and the age of the newest quote shown for context only. A withheld wing is not a required input: it has no volatility (the cell says why), is left out of the smile, and is counted.

**What a decision records:** per contract side (`SideView.quality`): the state, every flag, which of them withheld and which labelled, the price basis (`mid` or `last`), the book, trade states, and the inputs (now, the age base, receipt, book-seen, book time, trade time, the basis of the book time, book and trade ages, bid, ask, last, spread, delivery delay, out-of-order count, the forward's time and the sync gap) and the policy id and version.
