# WP07 T6: bounded queued work (16 November 2026)

Finding (terminal-review T6): operation timeouts did not bound queue time. `analyse_worker.rs` waited for its mutex before its 300 s answer timeout began; `helper.rs` waited for a slot before its response deadline; startup had its own 180 s / 60 s limit on top; a timed-out child was dropped (`kill_on_drop`) without anyone confirming it had exited; the UI had a per-view busy guard but there was no server-wide queue contract. Plan: [WP07-PLAN.md](WP07-PLAN.md), "T6: bounded queued work". **Status: implemented offline; the review's items R1 to R4 are addressed in the last section ("T6 review corrections") and T6 awaits re-review. T8 stays paused. Nothing was committed or pushed; no production data, environment file or live call was used.**

Evidence: [baselines/wp07-t3r-2026-11-16/README.md](baselines/wp07-t3r-2026-11-16/README.md), section "T6 runs".

## The rules, and the tests that pin them

States: `queued`, `running`, `done`, `failed`, `cancelled`, `expired`, `cancel_unconfirmed`. Every accepted job has an ID. One deadline per job, from its submission.

## Compatibility effects

- `AnalyseError` gains three variants; `analyse_error_response` is the one mapping for both routes (the old answers are unchanged: 400, 502, 422).
- `Helpers::run`'s `limit` is now a **total** time. The callers pass limits written for the answer alone (30 s for the Fundamentals page and the valuation, 25 s for the adjusted daily bars, the board's own for the board); a request that waits behind another now has less time than before. That is the finding's point, but it can turn a slow second request into a fallback to the direct command.
- A helper or the analysis worker that times out is now **ended and confirmed** before its slot is used again, so the next request after a timeout waits for the termination (up to two grace waits: 5 s each for the analysis worker, 2 s for helpers) and then for a fresh child's start (about 15 s for the analysis worker).
- Dropping a job's `Ticket` cancels the job: a queued job disappears; a **running** job's child is ended and the analysis worker restarts for the next request. axum drops a handler's future when the client disconnects, so a person who navigates away from a long analysis would cost the worker's warm state. That path is tested at the pool level (dropping the ticket); **a real client disconnect through HTTP was not tested**.
- New routes `GET /api/work` and `POST /api/work/resolve` are under the existing Host/Origin guard.
- Existing tests are unchanged except `bounded`'s own; no existing assertion was edited.

## Limits and what is not established

- **Capacities are not calibrated on real load**: analysis 1 worker + 4 waiting, 300 s; helpers 2 workers + 8 waiting; board helper 1 + 8. They keep the previous worker counts.
- **(Superseded by the review corrections below.)** ~~The helper fallback is not queued: when a helper is unavailable (queue full, deadline, held), the caller runs the Python command itself; those direct runs are not bounded by T6.~~ A refused, expired or unconfirmed helper request no longer runs the command at all, and the command run after a helper that certainly finished shares the request's one deadline and admission. Other job managers (`verdict_job.rs`, `forensic_job.rs`, `fund_fetch.rs`, `sentiment.rs`, `ipo.rs` and the Python supervisor) have their own mechanisms and were not changed.
- **Confirmation is for the direct child only** (as for T4): a worker that started its own subprocesses is not followed. On Windows `kill` ends the process, not its descendants.
- **The job records live in memory** (the last 200 finished jobs are kept). **Held workers are also written to a journal file** (T6 review, R3, below), because nothing in the terminal can end a child once the terminal itself is gone. An earlier version of this record said the children "end with it through `kill_on_drop`"; **that was not supported and is withdrawn**: `kill_on_drop` ends a child whose handle this process drops while it is alive, and it does nothing when the terminal crashes or is killed (on Windows a killed parent leaves its children running).
- The caller is told at the deadline while the child is still being ended; a new job cannot take that worker until the exit is confirmed, so it waits (on its own deadline).
- Tests with real children use real short timers (1.2 s answers, 0.3 s grace) beside the paused-clock tests; they were run repeatedly (see the run table) but a heavily loaded machine could make their bounds tight. **That happened once in the review's verification runs** (`…203737-rust-t6r-verify-a`, kept): `analyse_worker::the_deadline_includes_the_wait_…` failed because its first request had 2 s for a Python start **and** a 1.2 s answer. That was a timing flaw in the first version of the test, not in the code; it and its neighbour (800 ms deadline near a Python start) now warm the worker first and the neighbour has 2.5 s. They are still real-timer tests.
- The termination routine is exercised against fake children (every ordering) and, for real, against a Python child that ignores its input closing (so the kill step runs). No real model call, no real warehouse and no real terminal session was used.
- The mutation harness reads Rust results from libtest's text (the v2 harness, see the T3 record); a test meant to kill a mutant must fail by `assert_eq!`/`assert_ne!` (two tests were changed from `assert!(…, "msg")`/`expect` for that reason).

### The rules, stated once

- **A stop wins.** Cancelled or expired before the child is spawned: no child. Before the request is sent: not sent. At the same instant as a reply: the stop.
- **Fall back only when the helper is certainly finished.** `Failed` (could not start, command failed, unusable reply, died with the child confirmed gone) allows one run of the command, inside what is left of the request's deadline. Refused, expired, cancelled and unconfirmed never do.
- **One deadline per request**, from the moment it arrives: the wait for a place, the helper and the command.
- **A held worker is identified** by pid and launch number, freed by confirmation, by a person (who and why recorded) or, after a restart, only by a person.

### Limits that remain

- **Restart handling is a record and a refusal to guess, not a cleanup.** If the terminal is killed while a child is held, the child keeps running until a person ends it. A child that was running normally (not held) when the terminal was killed is not in the journal at all: it is simply orphaned, and nothing here changes that. Ending process trees (Windows job objects) would, and is not built.
- The journal is only as good as the last write: it is written when a worker is held and when it is freed, not on every change, and a terminal killed between the hold and the write loses the entry. `pid` reuse by the operating system after a long gap is a real hazard for a person checking a pid; the entry says when it was written (`since_unix_ms`).
- `confirmed_gone` is a person's word; the terminal cannot check it.
- A request that fails after being sent (`no_answer`) now takes the termination time (up to two graces) to be reported: the price of never running work beside a child that may still be going.
- The helper pools' deadline and the admission's wait are separate machinery that share one `Budget` per request; a request that arrives at an admission with nothing left is refused as expired, not queued.
- Not changed: `verdict_job.rs`, `forensic_job.rs`, `fund_fetch.rs`, `sentiment.rs`, `ipo.rs` and the Python supervisor still have their own mechanisms and no kind telemetry.
- No real client disconnect through HTTP, no real terminal session, no live call and no production `.athena` file was used. The journal is exercised in a temporary folder.

### The policy decisions, applied

- **Returning at the deadline is acceptable while cleanup retains ownership and capacity.** That is now true of pool workers (as before) and of direct commands (gap 1).
- **Ticket lifetime (R2).** Dropping a `Ticket` now **abandons** the job: a **queued** one is cancelled, one a worker was given but has not started is stopped before it starts, and a **running** one (read-only analysis) is **let finish and its result is discarded**; its record says `abandoned`. A running job is stopped only by an explicit `Pool::cancel`. **Actual HTTP disconnects were exercised** over a real connection to the real server with a stand-in worker child: a client that gives up on a running analysis leaves the job `done`, `abandoned: true`, the worker's child unchanged (launch number 1, no restart, nothing cancelled), and the next request is served by the same child; a client that gives up while its analysis is queued has that job `cancelled_while_queued` while the running one finishes normally (`server::a_client_that_disconnects_from_a_running_analysis_…`, `…while_its_analysis_is_queued_…`). So axum/hyper do drop the handler when the client goes.
- **Fallback only for explicitly idempotent operations (R3).** A confirmed exit after `no_answer` does not prove the operation never completed. `HelperResult::next(idempotent)`: a helper that never started (`start_failed`) always allows the command; a failure after the request was sent (`no_answer`, `command_failed`, `bad_reply`) allows it **only if the operation is declared idempotent** (`HelperOp::idempotent`, a match with no default: a new operation must say so; all four current ones only read), inside the original deadline; otherwise `Why::MayHaveRun`, told to the page as "not repeated because it may already have run" (`helper::a_failure_after_the_request_was_sent_allows_a_second_run_only_for_an_operation_known_to_be_safe_to_repeat`, `fundamentals`/`flow_board::a_stopped_helper_request_…`).
- **Journal and Windows Job Objects address different problems.** The portable recovery is fixed first (above). Process-tree ownership (Job Objects, so that children and their descendants end with the terminal) remains a **separate enhancement, not built**.
